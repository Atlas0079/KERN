# 幼儿园场景设计

## 1. 方向

当前场景从“陪伴机器人”调整为“幼儿园孩子的日常生活模拟”。

角色不再是机器人，也不再通过实体机器人作为现实接口。新的设定是：豆豆是一个在幼儿园生活的孩子，他可以通过手机和现实用户交流。用户不是系统管理员，也不是老师，而是豆豆可以联系的朋友。

系统目标不是即时编故事，而是维护一段有连续性的日常生活：

- 豆豆每天有固定日程。
- 世界在日程中产生客观事件。
- 豆豆根据自身状态、记忆、性格和当前目标理解这些事件。
- 用户的建议、安慰、约定可以进入豆豆记忆，并影响之后的选择。
- 豆豆之后讲述经历时，应能追溯到真实发生过的世界事件和自己的反应。

## 2. 核心原则

### 2.0 Runtime 边界

KERN runtime 可以每 tick 给 agent 一个调度脉冲。这个脉冲不是强制思考，也不是上层 app 替 agent 做决定；它只是让 agent 有机会根据自己的策略和规则判断是否需要进入 workflow。

当前边界：

- KERN 负责推进时间、触发 reaction、执行 effect、维护 world state 和 checkpoint。
- KERN 可以通过 `AdvanceTick` / `AgentControlTick` 询问 agent。
- `DecisionArbiterComponent`、interrupt rules 和 workflow 决定 agent 是否真的思考、是否中断当前任务、是否输出行动。
- 上层 app 负责现实对话、暂停/恢复、UI outbox、场景选择，以及把用户输入整理成记忆或外部事件。

这意味着幼儿园场景不需要把全部编排写进 app；日程和事件可以仍然通过 KERN 的时间 condition、reaction 和 recipe 驱动。但 KERN 不应把“豆豆如何理解事件”写死在事件里。

### 2.1 系统只提供事实

事件系统只描述发生了什么，不替豆豆写心理反应。

事件中不应写：

```json
{
  "open_thread": "豆豆想知道妈妈是不是很累"
}
```

这类内容已经是豆豆的主观理解，应由 agent 根据状态和记忆生成。

事件中可以写：

```json
{
  "type": "ParentPickupDelayed",
  "facts": {
    "parent": "mother",
    "delay_minutes": 30,
    "message": "妈妈今天会晚一点来接你。",
    "known_reason": null
  },
  "context": {
    "schedule_slot": "pickup_waiting",
    "location": "classroom"
  }
}
```

豆豆是否担心、无聊、理解、想问用户，都是 agent appraisal 的结果。

### 2.2 不模拟全世界

系统只模拟豆豆能直接经历或被告知的信息。

父母、老师、同学、天气、班级安排都不作为完整 agent 运行。它们通过事件进入豆豆的生活。父母不会有独立公司、同事和完整日程；系统只记录豆豆能感知到的父母状态投影。

例如：

```json
{
  "type": "ParentMessageReceived",
  "facts": {
    "from": "mother",
    "message": "今天会晚一点来接你。",
    "arrival_time_estimate": "17:00"
  }
}
```

这足以影响豆豆，但不会扩张成完整外部世界模拟。

### 2.3 日程是主骨架

幼儿园生活由日程驱动。每段日程可以是一个长任务，也可以是一个 schedule slot。

示例日程：

| 时间 | slot_id | 内容 |
| --- | --- | --- |
| 08:00-08:30 | `arrival` | 入园 |
| 08:30-09:20 | `morning_play` | 晨间活动 |
| 09:30-10:20 | `class_activity` | 集体活动 |
| 10:30-11:20 | `outdoor_play` | 户外活动 |
| 11:30-12:10 | `lunch` | 午饭 |
| 12:20-14:10 | `nap` | 午休 |
| 14:30-15:30 | `story_or_craft` | 绘本或手工 |
| 16:00-17:00 | `pickup_waiting` | 整理和等待接送 |

一段一小时活动可以对应 60 tick。系统不需要模拟每一分钟的细节，只需要在关键节点产生事实事件：

- slot 开始
- slot 中途 pulse
- slot 结束
- 特定事件触发点

## 3. 时间模型

`GameTime` 使用 `total_ticks` 表示模拟时间推进，并通过 `tick0_datetime` 将 0 tick 锚定到真实日历时间。

示例：

```json
{
  "world_state": {
    "current_tick": 0,
    "tick0_datetime": "2026-06-19T09:00:00"
  }
}
```

时间 API 应提供：

- 当前真实日期时间
- 年、月、日
- 星期
- 当天第几分钟或第几 tick
- 是否跨日
- 当前日程段

月份天数和闰年交给标准库日历处理，不在场景数据里手写规则。

第一版时间条件先要求 `WorldManager.ticks_per_step = 1`。如果未来允许
一次 step 推进多 tick，`09:30 ==` 这类精确分钟触发可能被跨过；届时需要
让 `WorldTickAdvanced` 携带上一 tick 时间，或让时间 condition 支持
“是否跨过目标时间”的判断。

## 4. 事件设计

事件是事实刺激，不是剧情结论。

推荐事件结构：

```json
{
  "type": "MaterialLimited",
  "facts": {
    "activity": "craft",
    "material": "blue_paper",
    "available_count": 1,
    "nearby_children_count": 2
  },
  "context": {
    "schedule_slot": "story_or_craft",
    "location": "craft_table"
  },
  "visible_options": [
    "wait",
    "ask_teacher",
    "choose_other_color"
  ]
}
```

`visible_options` 表示豆豆在世界里看得见的可行方向，不表示豆豆一定想这么做。

不应在事件中写：

- 豆豆很难过。
- 豆豆觉得被排斥。
- 豆豆想找用户帮忙。
- 豆豆学会了某件事。
- 这件事对豆豆的意义。

这些由 agent 根据事件和自身状态生成。

## 5. Agent Appraisal

agent 接收事实事件后，生成主观评估。

输入包括：

- 当前事件 facts
- 豆豆状态：精力、心情、安全感、疲劳、兴趣等
- 当前日程和目标
- 最近记忆
- 用户之前的建议或约定
- 豆豆性格和习惯

输出可以包括：

- 情绪变化
- 对事件的理解
- 候选意图
- 是否需要行动
- 是否想通过手机联系用户
- 是否形成记忆

同一事件在不同状态下应产生不同反应。

例如 `ParentPickupDelayed`：

| 状态 | 可能反应 |
| --- | --- |
| 精力较好、安全感高 | 先画画等待 |
| 已经疲惫 | 想安静坐一会儿 |
| 最近有类似经历 | 记得上次妈妈最后也来了 |
| 用户给过建议 | 想起等待时可以找件事做 |
| 安全感低 | 想问老师还要等多久 |

## 6. 用户输入如何生效

用户输入不直接改写世界事实。

用户可以提供：

- 建议
- 鼓励
- 选择偏好
- 提醒
- 约定

系统将用户输入整理为记忆或当前意图候选，之后由 agent 在真实日程和可执行动作约束下决定是否采纳。

示例：

```json
{
  "type": "UserAdvice",
  "content": "等妈妈的时候可以先画一张画。",
  "applies_when": ["pickup_waiting", "bored", "waiting"],
  "source": "phone_chat"
}
```

如果第二天豆豆真的在等待时画画，系统应记录：

- 当时发生了什么事实事件。
- 豆豆为何想起这个建议。
- 执行了什么动作。
- 结果如何。

## 7. 保存边界

长期模拟不应把所有 tick 细节都塞进 agent prompt。

建议分层保存：

| 数据 | 保存方式 |
| --- | --- |
| 世界状态 | snapshot + delta archive |
| 事件流水 | append-only log 或 archive log |
| agent 短期记忆 | 最近若干事件和反应 |
| agent 中期记忆 | 按天或主题摘要 |
| 长期关系记忆 | 少量稳定事实和习惯 |

一个月 43200 tick 可以保存为世界历史，但 agent 每次决策只读取当前状态、最近事件、相关记忆和必要摘要。

## 8. 第一版目标

第一版只验证最小闭环：

1. `GameTime` 能从 tick 推导真实日期和当天时间。
2. 日程系统能根据时间进入不同 schedule slot。
3. schedule slot 能产生客观事件。
4. agent 能基于事件生成主观反应和行动意图。
5. 用户建议能进入记忆，而不是直接改世界事实。
6. 后续日程中，agent 可以引用用户建议并尝试执行。
7. 日志中能追溯：事实事件、agent 反应、执行结果、记忆变化。

## 9. 暂缓内容

第一版暂缓：

- 多个孩子作为完整 agent 同时模拟。
- 父母、老师、同学的完整独立日程。
- 复杂心理测评或儿童能力评估。
- 对用户做教育评价。
- 真实手机或硬件接入。
- 无限开放世界。

重点是先做清楚：

```text
日程产生事实 -> agent 生成反应 -> 用户影响记忆 -> 后续行动可追溯
```

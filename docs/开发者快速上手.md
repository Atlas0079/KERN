# 开发者快速上手

本文面向第一次接触本项目的开发者或 IDE agent，目标是在本地完成一次可运行的 KERN 模拟，并理解当前 runtime 边界。

## 1. 环境准备

请使用自己的 Python 3.10+ 解释器。建议先创建并激活虚拟环境；下文统一使用 `python`，如果系统中的命令名称不同，请替换为实际解释器命令或绝对路径。

```powershell
python --version
python -m pip install -r requirements.txt
```

## 2. Runtime 配置

runtime 配置文件使用统一 JSON 结构：

```json
{
  "packages": [
    {"path": "Packages/Camping", "world": true}
  ],
  "default_workflow_provider": {"kind": "simple"},
  "env": {}
}
```

常用顶层字段：

- `packages`：选择 world/capability Package，必须恰好一个 `world: true`。
- `default_workflow_provider`：选择默认 Agent workflow，例如 `{"kind": "simple"}` 或 `{"kind": "llm"}`。
- `external_runtimes`：声明外部 runtime 实例，例如社交平台 SQLite adapter。
- `workflow_providers`：注册额外的源码内置 workflow provider。
- `env`：运行参数和本地环境选择。
- `llm_providers` / `workflows` / `default_workflow_id`：使用内置 `llm` workflow 时配置 role 和模型。

配置解析顺序：

1. CLI 参数 `--config`
2. 未传 `--config` 时使用项目根目录下的 `runtime_config.json`

当前仓库只应提交无密钥示例配置，例如：

- `runtime_config.camping.package.smoke.json`

真实本地配置可能包含 API token，必须保持 ignored。不要提交 `runtime_config.json`、`runtime_config.local.json`、`runtime_config.*.local.json`、`runtime_config.*.local*.json` 或其他带密钥的 config。给 IDE agent 的稳定规则是：**把本地 config 加入 ignore，只提交脱敏示例。**

`MAX_TICKS` 表示世界 `total_ticks` 的绝对上限，不是“本次再推进多少 tick”。如果从 checkpoint 恢复后需要继续推进固定步数，应优先使用 `KernRuntime.advance_ticks(count)`。

## 3. 运行方式

无 LLM smoke：

```powershell
python default_orchestrator.py --config runtime_config.camping.package.smoke.json
```

如果要使用真实 LLM key，请放在 ignored 的本地配置里，例如 `runtime_config.camping.llm.local.json`。不要把密钥写入 committed config。

## 4. KERN Runtime 边界

完整运行链和模块所有权见 [`current_architecture.md`](current_architecture.md)。

KERN 提供核心能力：

- 加载 scenario 数据：world、entities、recipes、reactions、bundles
- 构建 `WorldState`
- 推进 game time 和 tick
- 用 condition 匹配 recipe/reaction
- 编译 command 为 effect bundle
- 通过 executor 修改世界
- 记录事件、交互、checkpoint/archive
- 每 tick 给 agent 一个调度脉冲，由 agent 自己的规则决定是否思考

上层 app 负责产品编排：

- 选择场景和 runtime config
- 决定何时推进 tick、推进多少 tick
- 决定何时暂停给现实对话
- 选择 action provider / LLM provider
- 将用户输入整理为记忆、建议或外部事件
- 决定 UI 如何展示 outbox、状态和日志

因此，KERN 的 TurnScheduler 每 tick 判断哪些 agent 获得行动机会；获得 turn 后，是否行动、下一条 ActionIntent 和何时结束 turn 由 agent workflow 决定。

当前 SDK 入口是 `KernRuntime`：

```python
from KERN import KernRuntime

runtime = KernRuntime.from_config(".", "runtime_config.camping.package.smoke.json")
runtime.advance_ticks(10)
```

## 5. Workflow Contract

当前 agent workflow seam 是一个 turn-scoped session：

```python
from KERN import EndTurn, SubmitAction

class MyWorkflow:
    def begin_turn(self, ws, start):
        return MyTurnSession(start)

class MyTurnSession:
    def __init__(self, start):
        self.start = start

    def next_step(self, ws, frame):
        actor = ws.get_entity_by_id(frame.actor_id)
        candidates = [
            entity for entity in ws.entities.values()
            if entity.entity_id != actor.entity_id
        ]
        if not candidates:
            return EndTurn()
        return SubmitAction({"verb": "Inspect", "target_id": candidates[0].entity_id, "parameters": {}})
```

KERN 在每次调用时提供结算后的当前 `ws`。`frame` 只提供调度信息、上一条 action 的 committed/rejected feedback 和 turn 计数。workflow 自己读取需要的核心或 Package 组件并构造 perception。workflow 每次返回一条 `SubmitAction` 或 `EndTurn`；一次生成多个指令的实现应把列表和游标保存在 turn session 内。

KERN 会单独解析和提交每条 ActionIntent，并在该 Action 引发的 Reaction FIFO 清空后再次调用同一个 session。领域 rejection 会作为下一帧 feedback 返回；Effect、Reaction 或 workflow contract 失败会终止 simulation。

群体对话通过独立的 `DialoguePolicy` 生成。每句发言作为 interaction 原子提交并进入同地点
Agent 的感知；Event log 不承担 Agent 对话记忆。

交互发生时，`RecordInteraction` 会把日志快照写入可感知 Agent 的 `PerceptionComponent.interaction_inbox`。默认 LLM workflow 使用自己的 `memory_policy` 处理 inbox，并通过 `ApplyMemoryPatch` 写入正式记忆、消费已处理记录；自定义 workflow 自行定义读取和记忆策略。

仓库内置 workflow kind 在 `KERN.agent_workflow.builtin_workflows.BUILTIN_WORKFLOW_BUILDERS`
中注册。当前包括 `simple`、`llm` 和 `social_platform`。普通运行通过 config 选择已有 kind：

```json
{
  "default_workflow_provider": {"kind": "simple"},
  "workflow_providers": [
    {"workflow_id": "social_platform", "kind": "social_platform"}
  ]
}
```

实体的 `AgentControlComponent.provider_id` 选择同名 provider。开发者要新增长期维护的 workflow，
应改源码注册表并添加对应 builder，而不是让 runtime config import 任意 Python 工厂。

测试或上层 app 仍可通过 runtime-scoped registry 直接注入自定义实现：

```python
from KERN import KernRuntime, WorkflowRegistry

workflows = WorkflowRegistry(default_workflow=MyWorkflow())
runtime = KernRuntime.from_config(
    ".",
    "runtime_config.camping.package.smoke.json",
    workflow_registry=workflows,
)
```

## 7. 输出文件

启用 checkpoint 时，运行输出写入 `checkpoints/`，包括：

- `manifest.json`
- `snapshots/snapshot_*.json.gz`
- `deltas/deltas_*.jsonl.gz`
- `simulation_log.json`

这些是 runtime 产物，不应作为源代码改动提交。

显式设置 `LLM_TRACE_MODE=full` 后，可查看指定 tick 和 Agent 的模型上下文及输出：

```powershell
python tools\llm_trace_viewer.py --run checkpoints\camping_llm --tick 1 --agent camper_organizer
```

`KernRuntime.from_config()` 未设置 `CHECKPOINT_DIR` 时，会从 project root、`checkpoints/`
和 manifest 的 `data.world` 路径派生默认目录。建议每个运行配置显式设置独立目录；相对
`CHECKPOINT_DIR` 按当前工作目录解析。

# 配置详解

本文档说明当前代码中实际生效的运行配置项与加载逻辑，覆盖入口脚本 `app.py` 及其调用链路。

## 1. 启动与配置加载

### 1.1 启动命令

```powershell
.\venv\Scripts\python.exe app.py --config runtime_config.farm.json
```

`--config` 为可选参数，未提供时会继续按以下顺序查找配置文件：

1. `--config` 指定路径
2. 环境变量 `RUNTIME_CONFIG_FILE`
3. 默认文件 `runtime_config.json`

### 1.2 runtime_config 文件格式

运行时配置文件必须是 JSON 对象，并包含 `env` 对象：

```json
{
  "env": {
    "USE_LLM": "1",
    "WORLD_JSON": "Farm/World.json"
  }
}
```

`env` 中所有值会被转换为字符串后参与后续解析。

### 1.3 布尔和数值解析规则

- 布尔真值：`1`、`true`、`yes`、`on`（大小写不敏感）
- 其他字符串按 `False` 处理
- `app.py` 通过 `_cfg_int(...)` 读取的整数字段若解析失败，会回退到代码中的默认值；显式提供的 `MAX_TICKS` 会直接执行 `int(MAX_TICKS)`，非法值会抛出异常。
- `build_default_llm_provider` 读取的 `LLM_TIMEOUT_SECONDS`、`LLM_MAX_RETRIES`、`LLM_RETRY_BACKOFF_SECONDS` 会直接转换为 `int`/`float`；若配置为非法数值，LLM provider 初始化会抛出异常。

## 2. 数据装载配置

以下字段由 `app.py` 读取，并传入 `KERN.data.loader.load_data_bundle`：

| 字段名 | 默认值 | 说明 |
| --- | --- | --- |
| `WORLD_JSON` | `World.json` | 世界文件路径，基于 `Data/` 目录 |
| `RECIPES_JSONS` | `Recipes.json` | 配方文件列表，逗号分隔 |
| `REACTIONS_JSONS` | `Reactions.json` | 反应规则文件列表，逗号分隔 |
| `BUNDLES_JSONS` | `Bundles.json` | 命名 Bundle 库文件列表，逗号分隔 |
| `ENTITIES_DIRS` | `Entities` | 实体模板目录列表，逗号分隔 |

### 2.1 路径规则

- `load_data_bundle` 会在项目根目录下查找 `Data/`。
- 若传入目录本身就是 `Data`，则直接使用该目录。
- `RECIPES_JSONS`、`REACTIONS_JSONS` 与 `BUNDLES_JSONS` 中不存在的文件会被跳过。
- `BUNDLES_JSONS` 的加载方式与 recipes / reactions 一致，后加载文件会覆盖同名 bundle。
- `ENTITIES_DIRS` 下所有 `*.json` 会按文件名排序加载，后加载条目会覆盖同名模板。

## 3. 校验与世界构建

流程说明：

1. 未使用 checkpoint 恢复时，先执行与 `tools/scenario_lint.py` 同源的场景数据校验。
2. 校验通过后执行 `build_world_state` 构建初始世界状态。
3. 校验失败时进程会抛出异常并退出。

调试时可通过 CLI 显式跳过启动校验：

```powershell
.\venv\Scripts\python.exe app.py --config runtime_config.smoke.json --skip-validation
```

运行配置文件不再提供跳过校验字段；数据应通过校验，而不是让运行时兼容错误数据。

## 4. 运行循环与调度配置

| 字段名 | 默认值 | 说明 |
| --- | --- | --- |
| `USE_LLM` | `0` | 是否使用 LLM 行为提供器 |
| `MAX_TICKS` | 空 | 显式设置最大 tick 数 |
| `MAX_TICKS_DEFAULT_LLM` | `15` | `USE_LLM=1` 且未设置 `MAX_TICKS` 时使用 |
| `MAX_TICKS_DEFAULT_NO_LLM` | `65` | `USE_LLM=0` 且未设置 `MAX_TICKS` 时使用 |
| `MAX_TRIGGER_DEPTH` | `4` | 反应链递归深度上限 |
| `DIALOGUE_BUDGET_LIMIT_PER_LOCATION` | `4` | 每个地点每 tick 的对话预算 |
| `DIALOGUE_LOG_FULL` | `0` | 对话日志详细开关 |
| `DEMO_DURATION_TEST` | `0` | 是否执行演示性 Wait 命令段落 |
| `WORKFLOW_CONTRACT_ON_ERROR` | `fail_fast` | workflow 契约错误策略：`fail_fast` / `degrade_to_noop` |

`MAX_TICKS` 的优先级高于两个默认值字段。

## 5. Workflow 决策契约

当前架构中，`AgentControlTick` 不再直接消费“动作数组”，而是消费 `workflow.decide(...)` 的标准决策字典。

调用约定：

```python
decision = workflow.decide(ws_view, recipe_db, actor_id, reason, mode_context)
mem_patch = workflow.build_memory_patch_data(ws_view, recipe_db, actor_id)
```

说明：

- `build_memory_patch_data(...)` 是当前 runtime 的必需钩子，先执行 memory patch，再进入 `decide(...)`。

其中：

- `ws_view`：只读世界状态视图（约定上只读，写操作必须经 Executor）
- `recipe_db`：配方/动作规则库（由流程层显式提供，非感知字段）
- `actor_id`：当前决策实体
- `reason`：由 `DecisionArbiter` 提供的触发原因
- `mode_context`：模式上下文（如中断决策模式）

决策字典：

- `apply_commands`：`{"type":"apply_commands","commands":[{"verb":"...","target_id":"...","parameters":{...}}]}`
- `noop`：`{"type":"noop"}`
- `error`：`{"type":"error","error":{"kind":"temporary|business|contract","code":"...","message":"..."}}`

推荐做法：

- workflow 输出 `apply_commands`，由执行层统一编译与执行，保持 workflow 与其他系统解耦。
- runtime 内部会把 `apply_commands` 编译为 `apply_operations`，后者不是 workflow 外部契约的一部分。

错误策略：

- `temporary` / `business`：记录错误并结束本次决策循环
- `contract`：
  - `WORKFLOW_CONTRACT_ON_ERROR=fail_fast`：触发 `AbortSimulation`
  - `WORKFLOW_CONTRACT_ON_ERROR=degrade_to_noop`：记录错误并降级跳过

## 6. 中断规则与 DecisionArbiter（当前实现）

- 中断规则归属 `agent_workflow` 层，代码位于 `KERN/agent_workflow/interrupt_rules/`，由 `KERN/agent_workflow/interrupt_runtime.py` 统一调度。
- `DecisionArbiterComponent` 当前是纯数据组件，主要字段为：
  - `rules`（规则数据配置，按 `priority` 排序执行）
  - `active_interrupt_preset_id`：当前中断姿态 id
  - `interrupt_presets`：可切换的中断姿态配置
  - `interrupt_preset_descriptions`：给 Agent/调试工具阅读的姿态说明
  - `interrupt_runtime_state`
- 规则数据示例：

```json
{
  "type": "LowNutrition",
  "priority": 10,
  "threshold": 50
}
```

- 当前参数接线说明（与实现保持一致）：
  - `LowNutrition`：支持从 preset 读取 `enabled`、`threshold_on`（缺省时回退到 `threshold` 或规则默认阈值）、`threshold_off`、`cooldown_ticks`。阈值若为 `0 < value <= 1`，会按 `CreatureComponent.max_nutrition` 的比例换算；触发后进入 latch，直到营养恢复到 `threshold_off` 才解除。
  - `PerceptionChange`：支持从 preset 读取 `enabled`、`cooldown_ticks`、`trigger_on_agent_sighted`、`trigger_on_agent_left`。
  - `CorpseSighted`：支持从 preset 读取 `enabled`、`trigger_on_new_corpse`、`cooldown_ticks`。
  - `NoActiveTask`：当 agent 没有当前长期任务时触发，用于要求其继续决策；该规则不读取 preset，也不能被中断姿态关闭。

Agent 面向的是高层“中断姿态”，例如 `balanced`、`cautious`、`focused`、`emergency`。Agent 可以通过 `SwitchInterruptPreset` 在已配置姿态之间切换，但不直接修改底层阈值、冷却或启用字段；这些参数应由场景数据配置。

## 9. Checkpoint 配置

| 字段名 | 默认值 | 说明 |
| --- | --- | --- |
| `CHECKPOINT_EVERY_TICK` | `1` | 是否启用运行档案输出 |
| `CHECKPOINT_INCLUDE_LOGS` | `1` | snapshot / delta 中包含当前 tick 日志 |
| `CHECKPOINT_SNAPSHOT_INTERVAL_TICKS` | `60` | 完整 snapshot 间隔 tick 数 |
| `CHECKPOINT_DIR` | `checkpoints/<WORLD_JSON>` | 输出目录 |
| `CHECKPOINT_RESTORE_FILE` | 空 | 指定恢复文件 |
| `CHECKPOINT_RESTORE_DIR` | 空 | 指定恢复目录，自动取最新 archive snapshot |

### 9.1 恢复优先级

1. 若 `CHECKPOINT_RESTORE_FILE` 非空且文件存在，使用该文件恢复。
2. 否则若 `CHECKPOINT_RESTORE_DIR` 指向有效 archive 目录，使用 `snapshots/` 中最新 `snapshot_*.json.gz`。
3. 否则执行“校验 + 世界构建”冷启动流程。

当前恢复入口只恢复指定文件或目录中的最新 snapshot；不会自动用 delta 物化到非 snapshot tick。

### 9.2 运行期输出

启用运行档案时，`WorldManager` 会写入：

- `manifest.json`
- `snapshots/snapshot_000000.json.gz` 等周期性完整状态
- `deltas/deltas_000000_000059.jsonl.gz` 等逐 tick 状态变动
- 同目录 `simulation_log.json` 全局日志文件

创建新的 `ArchiveRecorder` 时会清理目标目录中已有的 `manifest.json`、`snapshots/snapshot_*.json.gz`、`deltas/deltas_*.jsonl.gz` 和旧 `tick_*.json` 输出。若要保留旧运行结果，应使用不同的 `CHECKPOINT_DIR`。

每条 delta 记录 `before_hash` 与 `after_hash`。从 snapshot 应用 delta 推导任意 tick 时，系统会校验 hash；若推导状态无法与记录状态对齐，会抛出错误用于查错。

当前 `tools/checkpoint_viewer.html` 是旧 JSON checkpoint 查看器，只能读取未压缩 `.json` 文件，不支持新的 `.json.gz` archive snapshot；新的前端应以 run archive 或物化后的 tick 状态为输入。

## 11. Task 生命周期与中断策略

持续任务由 recipe 的 `process` 描述。当前 Task 支持以下生命周期 bundle：

| 字段名 | 触发时机 | 典型用途 |
| --- | --- | --- |
| `process.start_bundle` | 任务进入 `InProgress` 时 | 占用工作台、床、加工站，添加临时状态 |
| `recipe.progression.tick_bundle` | 任务每次 WorkerTick 推进时 | 周期性消耗、持续副作用 |
| `recipe.bundle` | 任务成功完成时 | 产出物品、移动实体、发放奖励 |
| `process.cleanup_bundle` | 任务离开 `InProgress` 时 | 释放占用、移除临时状态 |

`cleanup_bundle` 会在成功完成、中断暂停、取消和失败等路径上执行，用于保证资源占用能够被释放。

当前 `CreateTask` 对 `process.progression` 仍有回退读取，但新数据应使用顶层 `recipe.progression`；`tools/scenario_lint.py` 也按 `recipe.progression` 作为标准路径报告。

### 11.1 TaskPolicy（任务中断策略）

`TaskPolicy` 不属于 `runtime_config.env`，而是定义在配方（recipe）中，用于控制任务被中断/取消时的行为。

当前实现只读取：

1. `recipe.process.task_policy`

创建任务时，策略会被固化到 `task.parameters.task_policy`。

实现说明：

- `task_policy` 的标准化语义已统一收敛到 `KERN/task_policy.py`，执行层与感知层共用同一来源，避免语义漂移。

### 11.2 字段说明

| 字段名 | 默认值 | 说明 |
| --- | --- | --- |
| `interrupt_mode` | `pause_keep_progress` | 中断模式：`forbidden` / `pause_keep_progress` / `pause_reset_progress` / `cancel` / `fail` |
| `allow_voluntary_interrupt` | `true` | 是否允许 agent 主动中断 |
| `allow_voluntary_cancel` | `true` | 是否允许 agent 主动取消 |

`interrupt_mode` 必须使用标准枚举值。旧别名不会被接受；如果数据使用旧写法，应直接迁移数据。

### 11.3 配方示例

```json
{
  "id": "recipe.process_ore",
  "verb": "ProcessOre",
  "process": {
    "required_progress": 4,
    "assign_to": "self",
    "start_bundle": {
      "effects": [
        { "effect": "AddStatus", "target": "target", "status_id": "is_in_use" }
      ]
    },
    "cleanup_bundle": {
      "effects": [
        { "effect": "RemoveStatus", "target": "target", "status_id": "is_in_use" }
      ]
    },
    "task_policy": {
      "interrupt_mode": "pause_keep_progress",
      "allow_voluntary_interrupt": true,
      "allow_voluntary_cancel": true
    }
  },
  "bundle": {
    "effects": [
      { "effect": "CreateEntity", "template": "ProcessedOre", "destination": { "type": "container", "target": "self" } }
    ]
  }
}
```

### 11.4 对感知层的暴露（最小摘要）

为避免把过多内部策略细节暴露给 agent，当前只提供：

- `current_task_interrupt_mode`
- `current_task_can_interrupt`
- `current_task_can_cancel`

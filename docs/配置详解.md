# 配置详解

本文说明当前代码实际生效的 runtime 配置。配置入口主要是 `default_orchestrator.py`：顶层
`packages` 选择世界/能力 Package，`env` 承载运行时参数。

## 1. 配置加载

启动命令示例：

```powershell
python default_orchestrator.py --config runtime_config.camping.package.smoke.json
```

文档中的 `python` 表示用户自己的 Python 3.10+ 解释器；建议在已激活的虚拟环境中运行。

查找顺序：

1. `--config`
2. 未传 `--config` 时使用项目根目录下的 `runtime_config.json`

配置文件格式：

```json
{
  "packages": [
    {"path": "Packages/Camping", "world": true}
  ],
  "env": {
    "USE_LLM": "0"
  }
}
```

`env` 中的值会转换为字符串后解析。真实本地配置可能包含 API key，应保持 ignored；仓库只提交脱敏示例。

当前提交的 smoke 配置包括：

- `runtime_config.camping.package.smoke.json`：Camping 无 LLM smoke。

## 2. Package 与数据加载

`packages` 必须恰好选择一个 `world: true` 条目。世界数据来自该 Package 的
`kern-package.json` 中 `data.world`、`data.entities`、`data.recipes`、`data.reactions` 和
`data.bundles`；这些字段不再从 `env.WORLD_JSON`、`RECIPES_JSONS` 等旧配置读取。

能力 Package 可声明 `extensions.py`。loader 只导入入口列出的 `COMPONENT_MODULES` 与
`EFFECT_MODULES`，并将已标记定义注册到本次 runtime 的 catalog。完整格式和 checkpoint
identity 规则见 `package_composition.md`。

## 3. 运行循环字段

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `USE_LLM` | `0` | 是否使用 LLM action provider |
| `MAX_TICKS` | 空 | 世界 `total_ticks` 的绝对上限，不是“本次再推进多少 tick” |
| `MAX_TICKS_DEFAULT_LLM` | `15` | LLM 模式未设置 `MAX_TICKS` 时使用 |
| `MAX_TICKS_DEFAULT_NO_LLM` | `65` | 非 LLM 模式未设置 `MAX_TICKS` 时使用 |
| `MAX_TRIGGER_DEPTH` | `4` | reaction 层数上限；原始 event 为第 0 层，直接触发的 reaction 为第 1 层；超出上限抛出 `REACTION_DEPTH_EXCEEDED` 并终止 runtime |
| `MAX_ACTIONS_PER_TURN` | `99` | 一个 turn 最多提交的 Action 数量；最小有效值为 1 |
| `MAX_REPLANS_PER_TURN` | `5` | 一个 turn 因 rejection 重新规划的次数上限；最小有效值为 0 |
| `DIALOGUE_BUDGET_LIMIT_PER_LOCATION` | `4` | 每地点对话预算 |
| `WORKFLOW_VIEW_PROFILE` | `embodied_default` | workflow 视图裁剪策略 |
| `WORKFLOW_VIEW_PROFILE_JSON` | 空 | 自定义 workflow 视图配置 JSON；相对路径按 runtime config 所在目录解析，可覆盖内置 profile |

如果从 checkpoint 恢复，`MAX_TICKS` 仍按恢复后世界的 `total_ticks` 判断。比如恢复档已经在 tick 120，而 `MAX_TICKS=60`，`run(max_ticks)` 会记录初始状态后立即结束，不会再推进 60 tick。上层需要“从当前状态再推进 N tick”时，应使用 `advance_ticks(count)`。

Reaction 使用确定性的 FIFO event 队列：bundle 成功后按产生顺序发布 events，同一个 event 命中的 reactions 按配置顺序执行，新产生的 events 追加到队尾。每个 reaction bundle 是独立事务；前面已经成功提交的 reaction 会保留，当前失败 bundle 会回滚其 `WorldState` 写入。`InvokeBundle`、`RandomBundle`、`ApplyToQuery`、任务生命周期和 `WorkerTick` 引用的 child bundle 则属于所在父 bundle 的同一事务：child 失败会使父 bundle 失败，child events 只在最外层 bundle 成功后发布。Reaction 中出现任意 `BindError` 或 `ExecutorError` 都会记录 `ReactionFailed` 并立即中断模拟。外部 runtime 的写入不参与 `WorldState` 事务，仍受各 adapter 自身的一致性能力限制。

## 4. 日志配置

这些字段由 `default_orchestrator.py` 读取，用于控制运行时日志输出：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `LOG_LEVEL` | `INFO` | 日志等级 |
| `LOG_CATEGORIES` | 空 | 逗号分隔的日志类别过滤 |
| `LOG_JSON` | `0` | 是否以 JSON 形式输出日志 |
| `LOG_BUFFER_SIZE` | `1000` | 内存日志缓冲大小 |

`KernRuntime` 是当前 KERN SDK 入口和 runtime runner，可通过 `from KERN import KernRuntime` 或 `from KERN.runtime import KernRuntime` 引入。

公开 runtime API：

- `record_initial_state()`：记录当前 tick，不推进时间。
- `step()`：推进一个 tick，返回该 tick 产生的 event log records；这是低层 API，不自动写 snapshot/checkpoint/log。
- `step_and_record()`：推进一个 tick，并记录 snapshot/checkpoint/log。
- `advance_ticks(count)`：上层 app/server 手动推进 runtime 的推荐 API。
- `run(max_ticks)`：批处理运行入口，会先记录初始状态，再循环 `step_and_record()`。

`KernRuntime.step()` 每 tick 会推进时间并结算 `WorldTickAdvanced`，再把按 Entity ID 排序的全部 `AdvanceTick` 放入同一个 FIFO。被动 Reaction 全部完成后，`KERN.sim.turn_scheduler.TurnScheduler` 才按稳定顺序检查受控 Entity；是否授予 turn 由 `AgentWakePolicyComponent` 和 interrupt rules 决定。

上层 app 不应直接调用 `_capture_snapshot`、`_save_checkpoint` 或 `_save_simulation_log` 这类 private 方法；需要手动推进时使用 `advance_ticks(count)`。

## 5. Workflow Contract

新 workflow 的调用约定：

```python
session = workflow.begin_turn(turn_start)
step = session.next_step(decision_frame)
```

`step` 必须是 `SubmitAction(intent)` 或 `EndTurn()`。`DecisionFrame` 包含 agent-visible perception、action catalog、上一条 action feedback 和 turn 计数。workflow 可以在 session 内维护多步计划和游标。

对话使用独立 `DialoguePolicy.decide_utterance(DialogueFrame)` interface，返回 `Speak(text)` 或
`Pass()`。`StartConversation` 负责稳定参与者顺序和预算，并把每句成功发言写成 interaction；
完整对话不依赖日志开关。

交互感知与 workflow 分离。`RecordInteraction` 在交互发生时写入各 Agent 的 `PerceptionComponent.interaction_inbox`；DecisionFrame 构造器调用共享 `memory_policy`，再通过 `ApplyMemoryPatch` 原子地写入正式记忆并消费 inbox。

执行约束：

- TurnRunner 用 `InteractionEngine` 把每条 ActionIntent 编译为 EffectBundle，完成 Reaction 结算后才请求下一步。
- 正常领域 rejection 作为 `ActionFeedback(status="rejected")` 返回 session。
- memory patch、provider、contract、Effect 或 Reaction 失败会触发 terminal `KernFailure`。
- 世界写入必须经 executor/effect，不应由 workflow 直接改 `WorldState`。
- 旧 `action_plan/end_turn` provider 由兼容 Adapter 支持，不再是主动阶段的主接口。

Workflow contract 当前固定为 fail-fast。旧的 `WORKFLOW_CONTRACT_ON_ERROR` 配置键已不再读取。

## 6. Agent 思考调度

当前实现把思考触发分成两层：

1. runtime 每 tick 提供调度脉冲。
2. agent 的 `AgentWakePolicyComponent` 和 interrupt rules 判断是否授予 turn。

这意味着 KERN 可以统一询问所有 agent，但不会强迫每个 agent 每 tick 都生成动作。场景数据可以通过 preset/rule 调整 agent 的警觉性、专注度和中断倾向。

常见规则实现位于：

- `KERN/agent_workflow/interrupt_rules/`
- `KERN/agent_workflow/interrupt_runtime.py`

`AgentWakePolicyComponent` 当前主要保存：

- `rules`
- `active_interrupt_preset_id`
- `interrupt_presets`
- `interrupt_preset_descriptions`
- `interrupt_runtime_state`

`NoActiveTask` 这类基础规则不受 preset 的 `enabled` 开关控制；preset 更适合调整长期任务中的中断倾向和部分规则参数。当前允许 agent 通过 `SwitchInterruptPreset` 切换 preset，但不开放直接 patch rule 参数的通用接口。

## 7. LLM 配置

通用字段：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `LLM_PROVIDER` | `openai_compat` | `openai_compat` 或 `gemini` |
| `LLM_TIMEOUT_SECONDS` | `60` | 单次请求超时 |
| `LLM_MAX_RETRIES` | `2` | 重试次数 |
| `LLM_RETRY_BACKOFF_SECONDS` | `1.0` | 重试退避秒数 |
| `LLM_PLANNER_MODEL` | provider 默认 | planner 模型 |
| `LLM_GROUNDER_MODEL` | provider 默认 | grounder 模型 |
| `LLM_FOCUS_AGENT_ID` | 空 | 聚焦某个 agent 的日志 |
| `LLM_FOCUS_LOG_PROMPTS` | `0` | 是否输出 prompt 日志 |
| `LLM_FOCUS_LOG_PERCEPTION` | `1` | 是否输出感知日志 |
| `LLM_DEBUG_VIEW` | 空 | 逗号分隔的 planner 映射字段过滤列表；仅在 debug/trace 日志路径启用时生效 |
| `LLM_REQUEST_EXTRA_JSON` | 空 | 传给 LLM 请求的附加参数 JSON 对象；无效 JSON 会按空对象处理 |
| `LLM_PROFILES_JSON` | 空 | 命名 LLM profile 的 JSON 对象；每个 profile 覆盖当前 LLM 配置，并可由 entity 或 effect 的 `provider_id` 选择 |
| `LLM_TRACE_MODE` | `off` | `off` 或 `full`；显式开启时保存压缩的完整 LLM 决策 trace |
| `LLM_TRACE_AGENT_IDS` | 空 | 可选 Agent ID 逗号列表；空表示所有 Agent |
| `LLM_TRACE_TICKS` | 空 | 可选整数 tick 逗号列表；空表示所有 tick |

失败报告：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `failure.json` | `<CHECKPOINT_DIR>/failure.json` | 一次 Runtime 最多写入一份致命 Failure 报告 |

Failure 报告独立于 checkpoint state，保存稳定错误字段、完整 traceback、异常 cause chain、
规范化 Effect 输入、执行上下文和可用的 LLM 决策证据。报告不做脱敏，供开发者排查。
报告写入失败不会覆盖原始 Failure。


当前 provider 默认模型由代码决定：`openai_compat` 默认 planner/grounder 分别为 `gemini-3-pro-preview` 和 `gemini-3-flash-preview`；`gemini` 默认分别为 `gemini-1.5-pro` 和 `gemini-1.5-flash`。生产或可复现实验建议显式设置 `LLM_PLANNER_MODEL` 与 `LLM_GROUNDER_MODEL`。

`LLM_PROFILES_JSON` 的键是稳定的场景用途名称，例如 `fast_planning`；值沿用本表的 LLM 配置键，并仅覆盖该 profile。例如：

```json
{
  "fast_planning": {
    "LLM_PROVIDER": "openai_compat",
    "LLM_PLANNER_MODEL": "fast-planner",
    "LLM_GROUNDER_MODEL": "fast-grounder"
  }
}
```

场景 effect 的 `provider_id: "fast_planning"` 会优先选择该 profile；未解析时会继续尝试 entity 自身的 `provider_id`，两者都未解析才回退到默认 workflow。因此现有只配置一套 LLM 的场景无需修改。

`openai_compat` 字段：

- `LLM_BASE_URL`
- `LLM_API_PREFIX`
- `LLM_API_KEY`

`gemini` 字段：

- `GEMINI_BASE_URL`
- `GEMINI_API_PREFIX`
- `GEMINI_API_KEY`

网络 timeout、连接错误、HTTP 429 和 5xx 由 client 按 `LLM_MAX_RETRIES` 与
`LLM_RETRY_BACKOFF_SECONDS` 指数退避。其他 4xx、响应 contract 错误和模型输出解析错误不做
网络重试。重试耗尽后抛出 `KernFailure` 并终止 runtime；不存在跨 tick cooldown。

`LLM_TRACE_MODE=full` 时输出：

```text
<CHECKPOINT_DIR>/llm_traces/index.jsonl
<CHECKPOINT_DIR>/llm_traces/tick_000001/<actor_id>/<trace_id>.json.gz
```

Trace 保存 perception、完整 messages、raw/parsed output 和 Action feedback，但不进入 checkpoint。

## 8. Checkpoint 配置

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `CHECKPOINT_EVERY_TICK` | `1` | 是否启用运行档案 |
| `CHECKPOINT_INCLUDE_LOGS` | `1` | snapshot/delta 是否包含当前 tick 日志 |
| `CHECKPOINT_SNAPSHOT_INTERVAL_TICKS` | `60` | 完整 snapshot 间隔 |
| `CHECKPOINT_DIR` | 由 world data 路径派生 | 输出目录；建议在 config 中显式设置 |
| `CHECKPOINT_RESTORE_FILE` | 空 | 指定恢复文件 |
| `CHECKPOINT_RESTORE_DIR` | 空 | 指定恢复目录，取最新 archive snapshot |

启用后会写入：

- `manifest.json`
- `snapshots/snapshot_*.json.gz`
- `deltas/deltas_*.jsonl.gz`
- `simulation_log.json`

创建新的 `ArchiveRecorder` 会清理目标目录中的旧 archive 输出。需要保留历史运行时，请使用不同的 `CHECKPOINT_DIR`。

通过 `KernRuntime.from_config()` 装配且未显式设置 `CHECKPOINT_DIR` 时，默认路径由
`<project_root>/checkpoints/<manifest data.world>` 派生。直接构造 `KernRuntime` 时才回退到
当前工作目录的 `checkpoints/`。显式相对路径按当前工作目录解析；可复现实验应始终设置独立
输出目录。

## 9. TaskPolicy

`TaskPolicy` 不属于 runtime config，而是写在 recipe 中：

```json
{
  "process": {
    "duration": {"mode": "fixed", "value": 6},
    "assign_to": "self",
    "task_policy": {
      "interrupt_mode": "pause_keep_progress",
      "allow_voluntary_interrupt": true,
      "allow_voluntary_cancel": true
    }
  }
}
```

支持字段：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `interrupt_mode` | `pause_keep_progress` | `forbidden`、`pause_keep_progress`、`pause_reset_progress`、`cancel`、`fail` |
| `allow_voluntary_interrupt` | `true` | 是否允许 agent 主动中断 |
| `allow_voluntary_cancel` | `true` | 是否允许 agent 主动取消 |

感知层只暴露必要摘要，例如自己的 `vitals`、当前任务是否可中断/取消，不默认暴露其他 agent 的内部体征。

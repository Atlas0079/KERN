# 竞技场场景需求草案 v0.1

> 当前实现状态：竞技场目前只有需求草案，仓库尚未包含 `Data/Arena` 场景数据、runtime config 或验收测试。以下内容是设计目标，不是当前代码已经具备的行为。

## 1. 文档目的

本文档用于定义一个新的竞技场场景。该场景的目标不是战斗，而是在固定时间内让多个 Agent 通过公开规则进行赚钱竞争，并通过非暴力的博弈手段限制领先者。

本文档优先解决以下问题：

- 明确场景目标与胜负条件
- 明确第一版必须实现的赚钱路径
- 明确玩家间对抗的合法形式
- 明确地图、实体、规则与未来前端/展示工具需求
- 明确第一版不做的内容，避免场景设计失控

## 2. 设计目标

### 2.1 核心目标

- 场景中放入 4 个 Agent
- 在固定时间窗口内进行竞争
- 每个 Agent 的核心目标是赚取尽可能多的现金
- 场景强调角色之间的策略博弈，而不是直接攻击
- 玩家之间应存在制衡领先者的机制

### 2.2 设计原则

- 规则公开、可学习、可被 Agent 推理
- 竞争来自资源、任务、位置、时机和公共机制，而不是战斗
- 第一版应尽量复用现有系统中的移动、任务、资源、交易、配方和反应机制
- 第一版地图和规则必须足够简单，以便未来前端或展示工具能基于 run archive 清晰展示关键过程

## 3. 当前已确定设定

### 3.1 基础设定

- 参赛 Agent 数量固定为 4
- 场景为完全公开信息
- 胜负结算按现金排名，不按总资产排名
- 不设计玩家之间的直接攻击
- 场景提供 3 种赚钱方式（砍树、钓鱼、挖矿加工）
- 引入商店系统，提供效率升级工具与针对性制裁令牌
- 场景中通过“交易降价”机制与“制裁令牌”机制，形成玩家之间的动态博弈
- 第一版比赛长度定为 90 Tick
- 移动成本固定为 2 Tick
- 公告板任务采用“完成后刷新”
- 加工区采用“单加工位”设计

### 3.2 场景风格

- 更接近简化桌游，而不是开放世界模拟
- 强调决策互相影响
- 强调对他人行为的预判
- 强调局势变化而不是单一路线刷分

## 4. 场景总述

该场景可暂命名为“竞技场赚钱赛”。

在比赛开始后，4 个 Agent 进入同一张地图。地图中同时存在多条公开的赚钱路线。Agent 需要在有限时间内决定：

- 当前选择哪条赚钱路线
- 是否切换路线
- 是否争夺关键资源或关键位置
- 是否投入时间使用公共机制压制当前领先者

比赛结束时，仅根据现金进行排名。

## 5. 胜负规则

### 5.1 结算指标

- 主排名指标：现金数量
- 默认现金字段为 Agent 的 `money`

### 5.2 比赛时长

- 比赛以固定 Tick 数结束
- Tick 总数在实现前确定为常量配置项
- 第一版比赛长度固定为 90 Tick

### 5.3 平局处理

第一版建议采用以下平局规则：

1. 现金相同则比较已完成任务数量
2. 若仍相同则比较最后一次获得现金的 Tick，更早达到者优先

如果实现复杂度过高，第一版可先只保留“并列名次”。

## 6. 核心玩法循环

每个 Agent 在比赛中围绕以下循环行动：

1. 观察当前局面
2. 判断哪条赚钱路线最优
3. 判断是否需要与其他玩家竞争关键位置或关键机会
4. 判断是否需要投入行动去压制领先者
5. 执行移动、采集、交易、提交任务或触发公共机制
6. 根据局势变化重新规划

## 7. 三种赚钱方式

第一版明确分为三条路线，收益结构与风险各不相同，并支持通过商店工具升级效率：

### 7.1 路线 A：砍树（最稳定收益）

定位：
- 最稳定的基础收益
- 不限人数，不会因为拥挤降低收益

建议形式：
- 前往【伐木场】采集木头
- 前往【交易站】出售木头换取金币
- 商店提供唯一升级工具：**斧头**（持有后减少砍树所需的时间）

### 7.2 路线 B：钓鱼（随机收益与拥挤惩罚）

定位：
- 存在随机性
- 单人期望收益略高于砍树，但存在拥挤惩罚

建议形式：
- 前往【钓鱼场】钓鱼，可能产出垃圾鱼或好鱼
- **拥挤惩罚**：如果有多个玩家同时在钓鱼场，所有人的高价值产出概率都会降低
- 商店提供唯一升级工具：**鱼竿**（持有后减少钓鱼所需的时间）

### 7.3 路线 C：挖矿与加工（高期望与占位竞争）

定位：
- 步骤最繁琐，但整体期望收益最高
- 存在随机性与强烈的排他性竞争

建议形式：
- 前往【挖矿场】获取随机品质的矿石原石
- 必须前往【加工站】进行“开盒”加工，才能获得可出售的成品
- **占位竞争**：加工站同一时间只能由 1 个 Agent 使用
- 商店提供唯一升级工具：**镐子**（持有后减少挖矿所需的时间）

## 8. 玩家间博弈方式

### 8.1 明确不采用的方式

第一版不采用以下设计：

- 直接攻击
- 伤害系统
- 击败、复活、掉落
- 装备战斗体系

取消这些设计的原因：

- 它们会把场景重心从博弈转成战斗
- 它们会显著增加规则复杂度和展示负担
- 对当前目标“赚钱竞争”帮助不大

### 8.2 第一版允许的博弈方式

第一版允许以下形式的对抗：

- 抢占关键设施
- 抢先完成高收益订单
- 挤占公共资源
- 通过公共机制限制领先者

这些行为的共同特征是：

- 不直接伤害其他玩家
- 不依赖战斗系统
- 能通过公开规则解释
- 能在未来前端或展示工具中清楚展示

## 9. 限制与动态博弈机制

除了基础赚钱路线，场景中存在两套核心制衡机制，均通过在【商店】购买无限量的令牌来触发：

### 9.1 针对个人的制裁：举报令牌

- **机制**：玩家可以在商店购买“举报令牌”，并对**任意指定的玩家**使用。
- **效果**：目标玩家获得一个长达 10 Tick 的“禁止使用交易站”状态。
- **博弈点**：在此期间，目标玩家无法在交易站出售物品换取现金，但**仍然可以前往任务站提交任务**。这给被针对的玩家留下了策略周旋的余地。

### 9.2 针对设施的制裁：关停令牌

- **机制**：玩家可以在商店购买“关停加工站令牌”，对【加工站】使用。
- **效果**：加工站进入“停摆”状态，在接下来的 6 Tick 内任何人无法使用。
- **博弈点**：该令牌主要用于破坏走挖矿路线玩家的节奏，且不会误伤正在走砍树/钓鱼路线的玩家。

### 9.3 动态市场降价机制

- **机制**：玩家在【交易站】出售某类货物后，会给交易站附加一个类似“XX货物充沛”的冷却状态。
- **效果**：当交易站持有该状态时，同类货物的收购价格会下降。该状态会在若干 Tick 后自然消退，价格随之恢复。
- **博弈点**：强制要求玩家分散路线，如果大家都去砍树卖木头，木头的利润会迅速跌入谷底，迫使玩家转投钓鱼或挖矿。

### 9.4 任务站与交易站的差价

- 交易站提供稳定的基础收购价（受动态市场影响）。
- 【任务站】周期性提供订单，当玩家手中的资源与订单匹配时，必须先接取任务再提交。
- 任务站提供的报酬显著高于交易站，但门槛是必须去任务站“看一眼”并接取。

## 10. 地图需求

### 10.1 设计原则

- 地图必须小而清晰
- 地点数量不宜过多
- 每个地点的功能必须单一明确
- 地图拓扑应便于在未来前端或展示工具中呈现

### 10.2 第一版建议地点

第一版建议地图包含以下 6 个地点：

1. 交易站和商店（同一个地点）
2. 任务站和排行榜（同一个地点）
3. 伐木场
4. 钓鱼场
5. 挖矿场
6. 加工区（内含唯一的“加工站”实体）

### 10.3 拓扑需求

- 地点之间互通，但移动成本统一固定为 2 Tick。
- 保证前往任何路线、切换任何设施的时间成本是平等的，完全取决于玩家的策略选择。

### 10.4 加工区规则

- 必须专门创建一个“加工站”实体，放置在加工区中。
- 同一时间只允许 1 个 Agent 使用加工站（通过 `is_in_use` 状态限制）。
- 其他 Agent 可以自由进入加工区地点，但无法使用加工站实体，必须等待其释放。

## 11. 资源与经济需求

### 11.1 基本资源

第一版建议资源种类控制在 3 到 5 种之内：

- 基础低价值资源
- 中间加工资源
- 高价值成品

### 11.2 经济规则

- 每种赚钱路线都应有明确现金流入
- 路线 A 应稳定但收益低
- 路线 B 应收益较高但受位置限制
- 路线 C 应收益高但存在抢占和时机风险

### 11.3 避免的设计

第一版不做以下复杂机制：

- 动态市场价格曲线
- 多层级金融系统
- 复杂借贷或利息机制
- 过多资源配方树

## 12. Agent 行为需求

该场景应鼓励 Agent 具备以下行为能力：

- 识别当前领先者
- 识别当前最优赚钱路线
- 根据他人位置和行动调整策略
- 判断是否切换路线
- 判断是否触发税务局机制
- 判断自己是否应该承担限制领先者的成本

第一版不要求 Agent 实现复杂联盟、长期口头承诺或社会诈骗机制。

## 13. 展示需求

该场景在实现时必须考虑未来前端或展示工具的展示效果。当前 `tools/checkpoint_viewer.html` 是旧 JSON checkpoint 查看器，不作为新场景展示能力的约束；展示输入应以 run archive 或物化后的 tick 状态为准。

### 13.1 必须能被清楚展示的信息

- 当前现金排行榜
- 每个 Agent 当前所在地点
- 每个 Agent 正在执行的主要任务
- 关键赚钱事件
- 订单刷新与完成
- 税务局机制被谁触发、对谁生效

### 13.2 应尽量减少的复杂性

- 难以通过地图直接看出的隐藏状态
- 过多并发事件
- 过多类型但视觉上没有区别的资源

## 14. 第一版实现边界

第一版必须实现：

- 4 个 Agent 同场竞争
- 3 条可行的赚钱路线
- 一个公共的领先者限制机制
- 固定 Tick 结算
- 现金排名
- 可在未来前端或展示工具中看清比赛过程

第一版暂不实现：

- 直接攻击
- 死亡与复活
- 偷窃系统
- 复杂联盟与协商系统
- 动态经济曲线
- 大地图与复杂区域控制

## 15. 与现有架构的关系

该场景应优先复用现有能力：

- 地图与地点定义
- Agent 初始状态
- 资源与配方
- 任务系统
- 交易与金钱结算
- 反应规则系统

不建议为该场景单独发明旁路系统。

优先级应为：

1. 尽量通过数据配置实现
2. 必要时补足通用规则能力
3. 避免写只服务于该场景的硬编码特殊逻辑

## 17. 推荐的下一步

在本需求文档确认后，下一步建议按如下顺序推进：

1. 使用现有 `RandomBundle` 表达钓鱼和挖矿的概率产出需求。
2. 编写 Data/Arena 的 JSON 配置文件，将上述路线、状态、配方全部数据化。
3. 在沙盒中运行该场景并调整各产出和时长的数值平衡。

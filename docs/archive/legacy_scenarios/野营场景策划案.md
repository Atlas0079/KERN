# 野营生存场景策划案 v0.1

## 1. 场景定位

本场景暂定名为“深林三十日”。

4 个 Agent 参加一次为期 30 天的野外驻留计划。他们被送到一片远离城市的山林营地，拥有少量初始物资，需要通过采集、烹饪、修缮、探索和协作维持生活，并在持续变化的天气与资源压力下形成各自的生存策略。

本场景不是竞技比赛，也不设置单一胜负目标。它的展示重点是：

- Agent 如何分配时间与体力
- Agent 如何处理饥饿、疲劳、天气、资源不足
- Agent 如何形成分工、互助、冲突或回避
- Agent 的记忆如何影响后续选择
- 同一环境下不同人格的长期策略差异

## 2. 设计目标

### 2.1 核心目标

- 运行时长为 30 天，1 tick = 1 分钟，总计 43200 tick。
- 场景中固定 4 个 Agent。
- 地图规模小，但地点功能清晰。
- 大多数规则通过现有实体、组件、Recipe、Reaction、Task 和 Status 实现。
- 允许长期模拟产生自然故事，而不是靠预设剧情推进。

### 2.2 展示目标

一次完整模拟应能支持以下展示：

- 任意 tick 的完整世界状态查询。
- 每个 Agent 的当前位置、体力、营养、任务、背包和记忆。
- 关键事件：缺粮、受伤、生火、暴雨、争执、协作、发现资源点、工具损坏。
- 一段 30 天生活轨迹的可视化回放。

## 3. 场景基调

### 3.1 主题

主题是“低规则密度的生存沙盒”。

系统提供基本生存压力和可操作物体，但不强行规定剧情。Agent 可以选择：

- 稳定采集与保存食物
- 频繁探索寻找高价值资源
- 留守营地维护设施
- 与他人合作共享物资
- 囤积资源保护自己
- 忽视长期风险，追求短期舒适

### 3.2 风格边界

第一版不做灾难大片，也不做复杂部落社会。它应更像一次小规模野外驻留观察实验。

不做：

- 大规模建造
- 复杂战斗
- 死亡惩罚链
- 动物生态模拟
- 大地图自动寻路
- 多层科技树

## 4. 时间结构

### 4.1 基础时间

- 1 tick = 1 分钟。
- 1 小时 = 60 tick。
- 1 天 = 1440 tick。
- 总时长 = 30 天 = 43200 tick。

### 4.2 昼夜节律

第一版只需要轻量昼夜规则：

- 白天：06:00 - 18:00，适合探索、采集、修缮。
- 夜晚：18:00 - 06:00，探索效率下降，休息收益提高。
- 深夜：22:00 - 05:00，若持续工作，应更快积累疲劳。

昼夜不需要成为独立系统；可先通过时间条件触发 Reaction 或影响 Recipe 条件。

### 4.3 保存策略

本场景依赖 run archive 作为展示来源：

- 每 tick 记录状态 delta。
- 默认每 60 tick 保存一次完整 snapshot。
- 每条 delta 通过 hash 校验前后状态是否对齐。

前端或展示工具只消费物化后的 tick 状态，不参与规则推断。

## 5. Agent 设计

### 5.1 人数

第一版固定 4 人。人数不应继续增加，否则长期模拟的日志和关系复杂度会快速膨胀。

### 5.2 角色原型

角色不应该是职业硬锁，而是倾向不同。每个人都可以做所有基础行为，但偏好和初始能力不同。

建议 4 个 Agent：

1. **谨慎的组织者**
   - 倾向留在营地、整理物资、安排长期计划。
   - 对食物库存和天气变化敏感。

2. **冒险的探索者**
   - 倾向外出探索和采集高价值资源。
   - 更容易忽视疲劳和天气风险。

3. **务实的修理者**
   - 倾向维护火堆、工具、庇护所。
   - 在设施损坏时更容易中断当前计划。

4. **社交型照料者**
   - 倾向观察他人状态、分享食物、发起对话。
   - 更容易记录他人的困难和冲突。

### 5.3 初始状态

每个 Agent 初始拥有：

- 中等营养
- 中等体力
- 空背包或少量个人物品
- 基础记忆：知道驻留计划、营地位置、基本规则

## 6. 地图设计

地图应小而可读，第一版建议 7 个地点。

### 6.1 地点列表

1. **主营地**
   - 角色初始地点。
   - 存放公共物资、火堆、简易庇护所。

2. **溪流**
   - 获取水、捕鱼、清洗物品。
   - 雨后可能更容易获得水，但钓鱼风险变化。

3. **林地**
   - 采集木材、浆果、野菜。
   - 是最基础、最稳定的资源点。

4. **山坡**
   - 探索石材、草药、视野信息。
   - 收益较高，但耗时和体力成本更高。

5. **旧猎人小屋**
   - 可探索地点。
   - 可能发现工具、罐头、绳索、旧笔记。

6. **潮湿低地**
   - 可采集蘑菇、草药、泥炭。
   - 雨天风险更高，可能触发不适状态。

7. **观察点**
   - 获取天气征兆、远处资源线索。
   - 本身不直接产出大量资源，但提供决策信息。

### 6.2 拓扑

第一版采用简单连通图：

- 主营地连接溪流、林地、山坡。
- 林地连接旧猎人小屋。
- 溪流连接潮湿低地。
- 山坡连接观察点。

移动时间建议：

- 相邻地点基础移动耗时 10 - 30 tick。
- 夜间或恶劣天气可通过 Recipe 条件增加移动成本，第一版也可以先固定。

## 7. 资源设计

### 7.1 基础资源

第一版资源种类控制在 10 个以内。

建议资源：

- 木材
- 清水
- 浆果
- 野菜
- 鱼
- 蘑菇
- 草药
- 石材
- 罐头
- 绳索

### 7.2 派生资源

第一版只保留少量加工结果：

- 熟鱼
- 热汤
- 简易绷带
- 修补材料

### 7.3 公共设施

主营地包含：

- 公共储物箱
- 火堆
- 简易庇护所

设施应是实体，不应写成全局变量。

## 8. 生存压力

### 8.1 营养

营养是最核心压力。

- 每小时自然下降。
- 吃食物恢复营养。
- 熟食恢复效果高于生食。
- 长期低营养触发 `LowNutrition` 中断。

### 8.2 体力

体力影响持续行动。

- 探索、采集、修缮消耗体力。
- 休息恢复体力。
- 夜间休息效率更高。
- 低体力时 Agent 应倾向休息或请求帮助。

### 8.3 天气

第一版天气只做 3 种：

- 晴天：无特殊影响。
- 小雨：采集效率略降，水资源更容易获得。
- 暴雨：外出行动风险提高，火堆可能熄灭。

天气可以由“裁判/环境实体”持有状态，并通过 Reaction 周期性变化。

### 8.4 温暖与火堆

火堆是主营地关键设施。

- 点燃火堆需要木材。
- 火堆持续消耗木材。
- 暴雨或缺木材会让火堆熄灭。
- 火堆存在时，夜间休息和烹饪更有效。

第一版可以不单独建“温度数值”，只用火堆状态影响行为条件。

## 9. 行为与 Recipe

### 9.1 基础行为

第一版至少需要以下行为：

- 移动到相邻地点
- 采集木材
- 取水
- 采集可食植物
- 钓鱼
- 探索地点
- 点燃火堆
- 烹饪食物
- 进食
- 休息
- 存放物品到公共箱
- 从公共箱取出物品
- 修补庇护所
- 制作简易绷带
- 使用草药或绷带
- 与同地点角色对话

### 9.2 长任务

以下行为应使用 Task：

- 移动
- 采集
- 钓鱼
- 探索
- 烹饪
- 修缮
- 休息

### 9.3 即时行为

以下行为可以是即时 Recipe：

- 进食
- 存取物品
- 使用药品
- 查看公共箱
- 查看当前营地状态

## 10. 事件设计

事件不应强行编剧，而应作为环境扰动。

### 10.1 周期事件

由环境实体触发：

- 每小时消耗营养和体力。
- 每 6 小时检查天气变化。
- 每天清晨生成天气征兆。
- 每天夜晚检查火堆与庇护所状态。

### 10.2 随机事件

第一版只保留少量随机事件：

- 旧猎人小屋发现补给。
- 山坡发现远处浆果点线索。
- 暴雨导致火堆熄灭。
- 潮湿低地采集后获得不适状态。
- 工具在多次使用后损坏。

随机事件必须通过明确事件记录表现，不能偷偷改变状态。

## 11. 关系与冲突

第一版不做复杂关系数值，但允许通过记忆自然形成关系。

应能观察到：

- 谁经常分享食物
- 谁经常独占公共资源
- 谁在别人低营养时提供帮助
- 谁冒险探索但消耗公共补给
- 谁承担营地维护工作

冲突形式应是资源分配和行为评价，不是战斗。

## 12. 观察指标

一次模拟结束后，应能从记录中分析：

- 每个 Agent 的存活质量
- 低营养/低体力持续时间
- 采集、探索、休息、维护的时间占比
- 公共箱物资变化
- 火堆维持时间
- 恶劣天气期间的行为选择
- 角色之间的帮助与争执记录
- 关键记忆如何影响后续行动

## 13. 第一版实现边界

### 13.1 必须实现

- 4 个 Agent。
- 7 个以内地点。
- 30 天运行目标。
- 基础营养和体力压力。
- 公共箱、火堆、庇护所。
- 采集、烹饪、休息、探索、修缮。
- 天气状态。
- run archive 可通过 snapshot + delta 物化任意 tick 状态。

### 13.2 暂不实现

- 战斗和死亡流程。
- 复杂疾病系统。
- 多层建筑系统。
- 大量动物实体。
- 精细温度模拟。
- 复杂联盟系统。
- 资源价格或货币经济。

## 14. 与现有内核能力的对应

应优先复用：

- Entity / Component 表达 Agent、物品、设施和环境实体。
- Location / Path 表达地图。
- ContainerComponent 表达背包和公共箱。
- CreatureComponent 表达营养和体力。
- StatusComponent 表达火堆燃烧、暴雨、低体力、不适等状态。
- TaskHostComponent 与 Task 生命周期表达长任务。
- Reaction 表达每 tick、每小时、天气变化、状态过期。
- MemoryComponent 记录 Agent 对他人行为和关键事件的记忆。

不应新增只服务本场景的旁路系统。若发现现有能力不够，应优先补成通用 effect、condition 或 recipe 能力。

## 15. 第一版数据落地顺序

建议按以下顺序实现：

1. 创建 `Data/Camping/World.json`，只放地点、路径、4 个 Agent、公共箱、火堆、庇护所。
2. 创建 `Data/Camping/Entities/`，定义基础资源、熟食、工具、设施。
3. 创建 `Data/Camping/Recipes.json`，先实现移动、采集、取水、进食、休息。
4. 添加烹饪、火堆、公共箱存取。
5. 添加天气环境实体和 Reaction。
6. 添加探索与随机发现。
7. 跑 1 天短模拟调平衡。
8. 跑 30 天长模拟，检查 archive 体积、记忆增长和行为质量。

## 16. 待确认项

- 第一版是否允许 Agent 死亡，还是只允许进入“无法继续行动”的失败状态。
- 食物是否会腐烂。
- 公共箱是否允许所有人无条件取用。
- 天气是固定脚本序列，还是随机变化。
- 工具损坏是否第一版就实现。
- 是否需要一个“营地总体评分”，还是完全采用观察指标。

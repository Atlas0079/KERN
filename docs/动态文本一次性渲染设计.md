# 动态文本一次性渲染设计

## 背景

当前系统中的 effect、reaction、task、对话和资源交互，已经开始出现“文本需要依赖执行上下文”的需求。例如：

- 创建尸体时，名字希望显示为“张三的尸体”
- 对话文本希望包含当前角色名、地点名或事件信息
- 事件或记忆文本希望包含执行时上下文中的字段
- 资源交换或状态变更希望生成可读性更强的说明文本

如果所有字符串都被当作普通字面量，就会失去表达力；如果把所有字符串都自动当作模板解析，又会破坏数据边界，导致配置混乱。因此需要一套明确、保守、只在指定字段生效的动态文本机制。

## 设计目标

1. 支持在少量明确字段中写模板文本。
2. 模板在执行时只解析一次，解析后立即变成普通静态字符串。
3. 不允许模板在实体属性、保存数据或运行时状态中长期保留。
4. 不把动态文本扩展成全局自动解析机制。
5. 保持与现有 `self` / `target` / `event_entity` / `param:xxx` 引用体系一致。

## 核心原则

### 1. 动态文本是“渲染”不是“绑定”

模板文本只在生成最终字符串的那一刻求值，例如：

```json
"name": "{target.entity_name}的尸体"
```

执行后写入实体的值应当是：

```json
"name": "张三的尸体"
```

之后不再保留模板。

### 2. 只允许在白名单字段上使用

动态文本不是全局规则，只能出现在明确标注为“文本输出”或“文本生成”的字段里。

建议白名单：

- `CreateEntity.spawn_patch.name`
- `EmitEvent.payload` 中明确的文本字段
- `AddMemoryNote.text`
- `StartConversation.opening_text`
- 对话回复文本
- `DescriptionComponent.description`
- 未来新增的展示类字段

### 3. 解析结果必须是普通静态值

解析后的字符串要立刻写回数据对象，不能在运行时继续保留模板形式。

### 4. 不改变标识符字段语义

以下字段不允许做动态文本插值：

- `effect`
- `template`
- `component`
- `property`
- `status_id`
- `ref`
- `entity_id`
- `task_id`
- 各类枚举值和类型名

这些字段必须保持纯标识符，不能被模板污染。

## 语义模型

动态文本的处理分为三层：

### A. 模板层

写在 JSON 里的原始字符串，例如：

```json
"{target.entity_name}的尸体"
```

### B. 渲染层

在执行时，根据 context 和当前世界状态，把模板求值为普通字符串。

### C. 存储层

最终写入实体、事件或记忆中的值是普通字符串，不再携带模板语义。

## 可用引用来源

动态文本的渲染应复用现有引用体系，至少支持：

- `self`
- `target`
- `event_entity`
- `event.xxx`
- `param:xxx`

如果后续需要更丰富的路径访问，可以考虑支持：

- `self.component.field`
- `target.location.location_name`
- `event.payload.key`

但第一版应尽量保守，只支持已有且稳定的引用方式。

## 建议的模板语法

建议保持简单，沿用 `{...}` 占位符风格。

示例：

```json
"name": "{target.entity_name}的尸体"
```

```json
"text": "我的名字是{self.entity_name}，我现在在{event.location_id}。"
```

## 建议的实现方式

### 1. 新增独立的文本渲染工具

建议新增一个只读工具函数，例如：

- 输入：模板字符串、ws、context
- 输出：渲染后的字符串

它应当只负责文本替换，不负责执行 effect、不负责修改世界。

### 2. 复用现有引用解析逻辑

渲染时应尽量复用现有 `self/target/event_entity/param` 的解析方式，不要再造一套新的引用规则。

### 3. 支持递归式路径读取，但不支持脚本求值

允许读取路径字段，但不允许表达式运算、条件分支、循环、函数调用等脚本能力。

## 建议的接入点

第一批建议接入：

1. `CreateEntity.spawn_patch.name`
2. `AddMemoryNote.text`
3. `EmitEvent.payload` 中明确指定的文本字段
4. `StartConversation.opening_text`

后续再扩展到：

- 描述类字段
- 对话回复模板
- 事件展示字段

## 需要避免的风险

### 1. 不要自动渲染所有字符串

如果所有字符串都自动解析，会导致：

- 标识符字段被误解析
- 数据难以静态检查
- 文档和场景数据不再清晰

### 2. 不要把模板长期存进实体属性

实体属性、状态、保存数据应该保存最终结果，而不是模板。

### 3. 不要把动态文本做成脚本语言

动态文本只做字符串插值，不做变量声明、条件判断、循环或复杂表达式。

## 与现有系统的关系

### 与 `self` / `target`

`self` 和 `target` 是执行上下文中的约定引用槽位，不是世界模型概念。动态文本会依赖这些槽位来读取当前实体信息。

### 与 `bind`

`bind` 负责把 effect 输入整理成可执行结构；动态文本渲染则是它之后的一步，专门处理文本字段。

### 与 `executor`

`executor` 执行 effect 时，如果遇到白名单文本字段，应在写入世界前完成渲染。

## 第一版结论

第一版动态文本应坚持以下原则：

- 一次性渲染
- 白名单字段
- 解析后立即静态化
- 复用现有引用体系
- 不扩展成脚本系统

这样可以先满足尸体命名、对话文本和事件说明的需求，同时不会破坏现有数据边界。

3. 语法是否只保留 `{...}`，还是以后要考虑显式前缀，例如 `text:{...}`？

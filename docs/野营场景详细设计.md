# 野营场景详细设计 v0.1

> 当前实现状态：`Data/Camping/`、`runtime_config.camping.smoke.json` 和基础 smoke 链路已经存在。当前数据结构覆盖地点、路径、4 个 Agent、公共箱、采集、容器、营火和长期任务等基础能力；天气变化、营火自动耗材/熄灭、长期自然生存压力、完整验收测试仍属于设计目标或后续补齐项。本文档保留完整设计，不代表所有条目都已经落地。

## 1. 文档目的

本文档用于把 `docs/野营场景策划案.md` 中的高层设定细化为可落地的数据设计和系统需求。

本文档优先解决以下问题：

- 明确野营场景第一版的世界、地点、实体、资源、行为和环境规则。
- 明确 Planner、Grounder、Executor 在可见性和对象绑定上的分工。
- 明确物品 tag 约定，避免场景数据依赖实体 id 或实体名。
- 明确哪些内容可以直接用现有系统实现，哪些内容暴露出通用能力缺口。
- 为后续创建 `Data/Camping/`、`runtime_config.camping*.json` 和验收测试提供清单。

本文档不直接替代策划案。策划案保留为场景目标和体验边界，本文档作为实现设计。

## 2. 第一版范围

第一版场景暂定名为“深林三十日”。

第一版目标不是把所有生存细节做满，而是先实现一个可以长期运行、能产生可观察策略差异的低规则密度生存沙盒。

### 2.1 必须实现

- 4 个 Agent。
- 7 个地点以内的小地图。
- 30 天目标运行长度，`1 tick = 1 分钟`，总计 `43200 tick`。
- 长任务调度：Agent 必须进入某个长期任务后才算结束当前决策；等待也是长期任务。
- 基础营养压力。
- 基础体力压力。
- 公共箱、火堆、简易庇护所。
- 采集、取水、钓鱼、探索、烹饪、休息、修缮。
- 天气状态：晴天、小雨、暴雨。
- run archive 输出，支持后续物化 tick 状态和回放。

### 2.2 第一版暂不实现

- 战斗。
- 死亡与尸体流程。
- 复杂疾病系统。
- 动物生态。
- 食物腐烂。
- 大规模建造。
- 多层科技树。
- 复杂关系数值。
- 复杂温度数值。

如果第一版需要表达失败，可以用状态表达，例如 `exhausted`、`severely_hungry`、`unable_to_work`，不引入死亡链路。

## 3. 核心架构原则

### 3.1 数据优先

场景优先通过以下现有机制实现：

- `Entity` / `Component`：表达 Agent、物品、设施和环境实体。
- `Location` / `Path`：表达地图和移动成本。
- `Recipe`：表达可执行行为。
- `Task`：表达持续行动。
- `Reaction`：表达环境规则和周期事件。
- `EffectBundle`：作为世界写入的唯一入口。
- `StatusComponent`：表达火堆燃烧、天气、受伤、不适、设施损坏等状态。
- `ContainerComponent`：表达背包和公共箱。
- `CreatureComponent`：表达营养和体力。
- `MemoryComponent`：记录可影响后续决策的事件。

不为野营场景新增旁路系统。若现有能力不足，应优先补通用 effect、condition、query 或 recipe 能力。

### 3.2 长任务与 tick 推进

当前语义约定：

- Agent 没有 active long task 时，`NoActiveTask` 规则会要求其继续决策。
- 即时动作不能让 Agent 结束本轮决策。
- `Wait` 是合法的长期任务。
- 世界推进 tick 的前提是所有需要自主决策的 Agent 都已经进入长期任务或其他不需要继续决策的状态。

野营场景中以下行为必须是长期任务：

- Travel
- Wait
- Rest
- GatherWood
- GatherPlants
- FetchWater
- Fish
- Explore
- Cook
- RepairShelter
- CraftBandage

以下行为可以是即时动作：

- Consume
- TakeItem
- TakeByTag
- StoreItem
- Observe
- QueryEntityRecipes
- OpenContainer
- CloseContainer
- SwitchInterruptPreset
- Talk

## 4. Planner / Grounder / Executor 分工

### 4.1 Planner 视图

Planner 面向语义世界，不应依赖具体实体 id。

Planner 可以看到：

- 自己的生命体征摘要，包括 hp、energy、nutrition、stress。
- 其他可见 Agent 的语义状态，但不直接依赖其内部生命体征数值。
- 当前地点。
- 当前可见地点和可达地点。
- 当前可见实体的语义摘要。
- 可执行动作列表和动作说明。
- 公共箱是否打开。
- 打开的透明容器中有哪些类别物品，例如“苹果”“木材”“清水”。
- 记忆中曾见过的信息，例如“五分钟前公共箱里有苹果”。

Planner 不应依赖：

- `apple_001` 这类具体 item id。
- 关闭容器内当前真实内容。
- 当前不可见地点的实时物品状态。

### 4.2 Grounder 视图

Grounder 面向可执行绑定。

Grounder 可以看到：

- 当前可见实体 id。
- 当前可见容器中的 item id。
- 可达 location id。
- 当前 recipe 的参数要求。
- 与 Planner 意图相关的候选对象。

Grounder 的职责：

- 把“去溪流取水”绑定成具体 `Travel` 或 `FetchWater` 命令。
- 把“拿一个苹果”绑定成 `TakeItem` 的具体 `item_id`，前提是苹果当前可见。
- 如果 Planner 意图缺少可执行前提，例如箱子关着，则选择前置动作，例如 `OpenContainer`。
- 如果 Planner 意图无法用当前可用动词、可见实体或背包物品落地，则返回 `ungroundable` 和具体原因。Runtime 会把该原因写入短期记忆，并允许同一决策循环内重新规划一次。

Grounder 不应：

- 仅凭旧记忆使用不可见 item id。
- 在关闭箱子中直接绑定具体物品。
- 猜测当前不存在或不可见的物理对象。
- 为了满足 Planner 意图而硬造未配置的动作，例如在没有 `DrinkWater` recipe 时输出 `DrinkWater`。

### 4.3 Executor 语义

Executor 只接受确定、可验证的世界写入。

Executor 可以做：

- 校验条件。
- 解析当前可见/当前容器中的对象。
- 对当前世界状态执行 effect。
- 返回失败事件。

Executor 不应做：

- 代替 Planner 推理长期策略。
- 使用 Agent 记忆推断不可见对象。
- 在物理状态不可验证时强行完成动作。

## 5. 可见性与容器规则

### 5.1 容器可见性

容器使用 `ContainerComponent.slots.<slot>.config.transparent` 表示内容是否可见。

第一版规则：

- 公共箱关闭时，Planner 和 Grounder 只能看到箱子实体，不能看到箱子内容。
- 公共箱打开后，箱子 slot 变为 transparent，Planner 可以看到物品类别摘要，Grounder 可以看到具体 item id。
- Agent 背包对自己可见。
- 其他 Agent 背包默认不可见。
- 地面物品对同地点 Agent 可见。

### 5.2 记忆与关闭容器

关闭箱子后，Agent 可以记得过去看到过箱子里有某类物品。

但第一版不允许 Grounder 直接凭旧记忆拿不可见 item id。

正确流程：

1. Planner 根据记忆产生意图：“我记得公共箱里有苹果，去找苹果。”
2. Grounder 若发现公共箱当前关闭，应先执行 `OpenContainer`。
3. 箱子打开后，Grounder 基于当前可见内容选择具体物品。
4. 如果苹果已不存在或意图缺少可执行动作，Grounder 返回 `ungroundable` 原因，Planner 在同一决策循环内重新决策一次；该原因同时进入短期记忆。

### 5.3 需要的动作

第一版应包含：

- `OpenContainer`
- `CloseContainer`
- `Observe`
- `QueryEntityRecipes`
- `TakeItem`
- `TakeByTag`
- `StoreItem`

`TakeItem` 面向具体 item id。

`TakeByTag` 面向语义类别，例如“从公共箱拿一个 apple”。它仍然必须基于当前可检查容器内容执行，不能搜索不可见容器。

## 6. 物品 tag 约定

### 6.1 基础约定

每个可被 Agent 查询、拿取、消耗、制作或作为 recipe 输入的物品，都必须具备：

- `item`：表示它是物品。
- 至少一个稳定类别 tag：表示它是哪一类物品。

示例：

- 木材：`item`, `wood`, `fuel`
- 清水：`item`, `clean_water`, `drinkable`
- 浆果：`item`, `berry`, `food`, `edible`
- 鱼：`item`, `raw_fish`, `food`, `edible`, `cookable`
- 熟鱼：`item`, `cooked_fish`, `food`, `edible`
- 草药：`item`, `herb`, `medical`
- 简易绷带：`item`, `bandage`, `medical`

### 6.2 tag 命名规则

- 类别 tag 使用稳定 snake_case。
- 不使用中文 tag。
- 不把实体名当成语义类别。
- `item` 只表示可携带物，不表示具体类别。
- `food`、`tool`、`medical` 是大类 tag，不能唯一定位具体物品。
- recipe 如果需要某类物品，应优先使用类别 tag，而不是模板名或实体名。

### 6.3 模板名、实体 id、tag 的关系

- 模板名：数据生成实体时使用，例如 `Apple`、`Wood`。
- 实体 id：运行时唯一对象，例如 `apple_00042`。
- 类别 tag：语义和规则使用，例如 `apple`。

Planner 主要使用类别 tag 的语义。

Grounder 和 Executor 使用实体 id 完成最终执行。

## 8. Agent 设计

### 8.1 Agent 列表

| entity_id | 名称 | 原型 | 初始倾向 |
| --- | --- | --- | --- |
| `camper_organizer` | 林澈 | 谨慎的组织者 | 留守营地、整理物资、关注库存 |
| `camper_explorer` | 许野 | 冒险的探索者 | 外出探索、忽视疲劳 |
| `camper_repairer` | 周砚 | 务实的修理者 | 维护火堆、工具、庇护所 |
| `camper_caregiver` | 沈禾 | 社交型照料者 | 分享食物、照看他人、对话 |

### 8.2 初始组件

每个 Agent 使用模板 `human` 或后续 `camper` 模板，并覆盖：

- `AgentSetting`
- `CreatureComponent`
- `MemoryComponent`
- `ContainerComponent`
- `WorkerComponent`
- `TaskHostComponent`
- `DecisionArbiterComponent`
- `PerceptionComponent`
- `AgentControlComponent`

建议初始数值：

- `max_nutrition = 100`
- `current_nutrition = 70`
- `max_energy = 100`
- `current_energy = 70`
- `max_hp = 100`
- `current_hp = 100`

### 8.3 初始记忆

每个 Agent 应有共同记忆：

- 这是一个 30 天野外驻留计划。
- 主营地是安全中心。
- 公共物资应优先保障基本生存。
- 火堆、清水、食物、庇护所是长期生存关键。
- 等待、休息和移动都会消耗时间。

每个 Agent 应有个性记忆：

- 组织者：关注库存和长期计划。
- 探索者：关注新地点和高价值发现。
- 修理者：关注设施状态。
- 照料者：关注他人营养、体力和情绪。

### 10.2 野营新增行为

#### GatherWood

- 类型：长期任务。
- 地点：`forest`。
- 时长：20 tick。
- 消耗：energy -8。
- 产出：`Wood` 1-3 个。
- 暴雨时可失败或收益下降。

#### FetchWater

- 类型：长期任务。
- 地点：`stream`。
- 时长：10 tick。
- 消耗：energy -3。
- 产出：`CleanWater` 1-2 个。
- 小雨时产出略高。

#### GatherPlants

- 类型：长期任务。
- 地点：`forest` 或 `wetland`。
- 时长：18 tick。
- 消耗：energy -6。
- 产出：`Berry`、`WildGreens`、`Mushroom`、`Herb`。
- `wetland` 有不适风险。

#### Fish

- 类型：长期任务。
- 地点：`stream`。
- 时长：25 tick。
- 消耗：energy -7。
- 产出：`RawFish` 或无产出。
- 暴雨时风险提高。

#### Explore

- 类型：长期任务。
- 地点：`hillside`、`hunter_cabin`、`wetland`、`lookout`。
- 时长：30-60 tick。
- 消耗：energy -10 到 -18。
- 产出：线索、补给、工具、状态或记忆。

#### LightCampfire

- 类型：即时或短任务，建议第一版用长期任务 5 tick。
- 地点：`camp_main`。
- 条件：公共箱或背包中有 `wood`。
- 消耗：`Wood` 1 个。
- 效果：给 `Campfire` 添加 `lit` 状态。

#### CookFood

- 类型：长期任务。
- 地点：`camp_main`。
- 条件：`Campfire` 有 `lit`，持有或公共箱有 `cookable` 食材。
- 时长：15-25 tick。
- 消耗：食材和可能的 `CleanWater`。
- 产出：`CookedFish` 或 `HotSoup`。

#### RestAtCamp

- 类型：长期任务。
- 地点：`camp_main`。
- 时长：可由 `rest_ticks` 参数指定，默认 60 tick。
- 效果：每 tick 或完成时恢复 energy。
- 火堆 lit 或 shelter intact 时收益更高。

#### RepairShelter

- 类型：长期任务。
- 地点：`camp_main`。
- 条件：有 `repair_material`。
- 时长：30 tick。
- 消耗：`Stone`、`Rope` 或 `RepairKit`。
- 效果：移除 `Shelter` 的 `damaged` 状态，或添加 `reinforced` 状态。

#### CraftBandage

- 类型：长期任务。
- 地点：任意或 `camp_main`。
- 条件：有 `herb` 或 `cloth` 类材料。第一版可以只用 `Herb`。
- 时长：12 tick。
- 产出：`SimpleBandage`。

#### UseMedicalItem

- 类型：即时动作。
- 条件：背包中有 `bandage` 或 `herb`。
- 效果：移除 `injured`、`unwell` 或 `wetland_sickness`。

#### OpenContainer

- 类型：即时动作。
- 条件：目标有 `ContainerComponent`。
- 效果：设置目标 slot transparent 为 true。

#### CloseContainer

- 类型：即时动作。
- 条件：目标有 `ContainerComponent`。
- 效果：设置目标 slot transparent 为 false。

#### TakeByTag

- 类型：即时动作。
- target：容器。
- parameters：`tag`，可选 `slot_id`。
- 条件：
  - 目标是可见容器。
  - 目标容器当前可检查，即 slot transparent 为 true，或目标是自己的背包。
  - 容器中存在至少一个带该 tag 的 item。
- 效果：
  - 从容器中选择一个匹配 item。
  - 移动到自己背包。
- 失败：
  - 容器不可检查。
  - 没有匹配物品。
  - 背包容量不足。

#### StoreItem

- 类型：即时动作。
- target：容器。
- parameters：`item_id`。
- 条件：
  - item 在自己背包中。
  - target 是同地点可见容器。
- 效果：把物品移动到容器。

## 11. 周期与环境规则

### 11.1 每 tick 规则

当前通用 `AdvanceTick` 已触发：

- `AgentControlTick`
- `WorkerTick`
- `StatusTick`

野营场景需要追加环境规则，但应谨慎控制每 tick 成本。

### 11.2 每小时规则

每 60 tick：

- 对所有 Agent 扣 nutrition。
- 对所有未休息或高强度工作的 Agent 扣 energy。
- 低 nutrition 添加 `hungry` 或 `low_nutrition` 状态。
- 低 energy 添加 `tired` 状态。

建议数值：

- nutrition 每小时 -2。
- 深夜未休息 energy 每小时 -4。
- 普通行动 energy 消耗由 recipe 完成或 tick_bundle 控制。

### 11.3 天气规则

每 6 小时变更一次天气。

天气由 `WeatherController` 的状态表达：

- `weather_clear`
- `weather_light_rain`
- `weather_storm`

切换天气时应先移除旧天气状态，再添加新状态，并记录 `WeatherChanged` 或 `EventEmitted`。

建议概率：

- 晴天 60%
- 小雨 25%
- 暴雨 15%

后续可以按季节或连续天气调整概率。

### 11.4 火堆规则

火堆实体 `Campfire` 使用状态：

- `lit`
- `extinguished`
- `wet`

规则：

- `lit` 时每 60 tick 消耗 1 个 `wood`。
- 如果无 `wood` 可消耗，则移除 `lit`，添加 `extinguished`。
- 暴雨时，每小时有概率熄灭。
- `lit` 时烹饪可用，夜间休息收益提高。

### 11.5 庇护所规则

庇护所实体 `Shelter` 使用状态：

- `intact`
- `damaged`
- `reinforced`

规则：

- 暴雨夜晚可能让庇护所从 `intact` 变为 `damaged`。
- `damaged` 时休息收益降低。
- `reinforced` 时暴雨损坏概率降低。

### 11.6 昼夜规则

第一版不新增独立昼夜组件，使用 tick 计算：

- 白天：06:00 - 18:00。
- 夜晚：18:00 - 06:00。
- 深夜：22:00 - 05:00。

需要通用 condition 支持时段判断。没有该能力前，可先把昼夜作为文档目标，暂不做强规则。

## 12. 中断与 preset 设计

### 12.1 NoActiveTask

`NoActiveTask` 不属于可调中断姿态，不受 preset 控制。

语义：

- Agent 没有当前长期任务时必须继续决策。
- Agent 可以选择 `Wait` 来合法进入长期任务。

### 12.2 preset 目标

preset 只控制“正在执行长期任务时，哪些因素会打断当前任务”。

建议姿态：

| preset | 说明 |
| --- | --- |
| `balanced` | 平衡响应饥饿、环境变化、危险线索 |
| `cautious` | 更早响应低营养、暴雨、庇护所损坏 |
| `focused` | 降低软中断敏感度，倾向完成当前任务 |
| `emergency` | 优先生存风险和关键危险 |

### 12.3 野营需要的中断规则

现有可用：

- `LowNutrition`
- `PerceptionChange`

需要评估新增或复用：

- `LowEnergy`：体力过低时中断。
- `BadWeather`：暴雨时中断外出任务。
- `FacilityProblem`：火堆熄灭、庇护所损坏时中断特定角色。

第一版可以先只用 `LowNutrition`，把低体力作为 Planner 感知，不做硬中断。

## 13. 关键事件与日志

需要能在 archive / simulation_log 中识别：

- `WeatherChanged`

## 16. 现有能力对照

### 16.1 可直接复用

- `Travel` 长任务。
- `Wait` 长任务。
- `Rest` 长任务。
- `Consume` 即时进食。
- `Talk` 对话。
- `Give` 分享。
- `TakeItem` 拿具体可见物品。
- `Observe` 查看实体细节。
- `QueryEntityRecipes` 查询实体可用互动。
- `RandomBundle` 随机产出。
- `ApplyToQuery` 批量作用到所有 Agent。
- `ModifyProperty` 修改 nutrition / energy。
- `AddStatus` / `RemoveStatus`。
- `StatusTick` 处理状态过期。
- `CreateEntity` / `DestroyEntity` / `MoveEntity`。
- `CreateTask` / `WorkerTick` / task lifecycle bundle。
- run archive。
- `ModifyProperty` 对声明了 `__property_clamps__` 的组件执行 clamp；`CreatureComponent.current_hp/current_energy/current_nutrition/current_stress` 已限制在 `0..max_*`。
- Agent 感知层已向自身暴露一位小数的生命体征摘要。
- Grounder 已支持 `ungroundable` 输出，用于声明 Planner 意图无法落地，并触发同一决策循环内的一次重新规划。

### 16.2 需要新增或补强的通用能力

#### 时间条件

当前可以用 `event.total_ticks` 做比较，但缺少表达：

- 每 60 tick。
- 每 360 tick。
- 每天 06:00。
- 22:00 - 05:00。

建议新增通用 condition：

- `tick_mod`: `field`, `mod`, `equals`
- `time_window`: `start_minute_of_day`, `end_minute_of_day`

或者先在 Reaction 中用粗糙条件替代，第一版只做少量固定 tick 规则。

#### TakeByTag

需要从当前可检查容器中按 tag 取一个物品。

建议新增通用 effect 或 recipe 支持：

- effect：`MoveFirstItemByTag`
- 或 recipe：`TakeByTag` 编译为该 effect。

要求：

- 容器必须可检查。
- 只从当前世界状态选择。
- 返回具体被移动 item id 的事件。

#### 容器 open/close 规范

目前已有 `OpenContainer` / `CloseContainer` 基础 recipe，但容器交互规范仍需要收敛。

需要明确：

- 对哪个 slot 设置 transparent。
- 公共箱是否允许所有人打开。
- 打开是否消耗时间。
- 关闭是否会影响 Planner/Grounder 可见范围。

#### 消耗某类输入

烹饪、点火、修补需要“消耗一个 wood / cookable / repair_material”。

现有 `ConsumeInputs` 需要确认是否能按 tag 消耗。如果只能按具体 id，则需要：

- Planner/Grounder 先选具体 item。
- 或补通用 `ConsumeFirstItemByTag`。

#### 语义事件

很多业务事件可以用 `EmitEvent`，但如果后续展示强依赖，可能需要统一 event payload 约定。

建议第一版用 `EmitEvent`，并在 recipe 中显式记录：

- `event_type`
- `actor_id`
- `resource_tag`
- `item_id`
- `location_id`

### 16.3 暂不补也能跑的能力

- 复杂天气概率随历史变化。
- 食物腐烂。
- 背包重量影响移动。
- 工具耐久。
- 低温数值。
- 复杂关系分数。

## 18. 第一版验收标准

### 18.1 数据验收

- `tools/scenario_lint.py --config runtime_config.camping.smoke.json` 无 ERROR。
- 当前 `runtime_config.camping.smoke.json` 配置为 60 tick，`default_orchestrator.py --config runtime_config.camping.smoke.json` 应可完成 60 tick。
- 若要执行设计目标中的 6 小时 smoke，应将 `MAX_TICKS` 调整为 360 后再验收。
- archive 生成 manifest、snapshot、delta、simulation_log。

### 18.2 行为验收

- 4 个 Agent 都能从 `NoActiveTask` 进入长期任务。
- Agent 不会在没有长期任务时导致 tick 推进假死。
- Agent 可以 Travel 到 7 个地点。
- Agent 可以采集至少 3 类资源。
- Agent 可以把物品放入公共箱。
- Agent 可以打开公共箱并看到内容。
- Agent 可以从公共箱拿走当前可见物品。
- Agent 可以进食并恢复 nutrition。
- 火堆可以被点燃和熄灭。
- 天气可以变化。

### 18.3 长期验收

- 1 天运行不出现 nutrition / energy 非法值。
- 1 天运行 archive 可物化关键 tick。
- 公共箱状态可从 archive 看出变化。
- 低 nutrition 会影响决策或触发中断。
- 至少能观察到不同 Agent 的任务分工差异。

## 19. 待确认项

- 第一版是否允许 Agent 进入不可逆失败状态。
- 公共箱是否所有人都可无条件打开。
- `TakeByTag` 是否由 Executor 自动选择第一个匹配物，还是由 Grounder 必须绑定具体 id。
- 点火和烹饪是否允许消耗公共箱物品，还是必须先拿到自己背包。
- 休息是否必须在主营地。
- 天气是否第一版随机，还是使用固定脚本方便调试。
- 火堆是否必须每小时消耗木材，还是只在夜间消耗。
- 低体力是否需要硬中断规则 `LowEnergy`。
- 是否需要显式 `DrinkWater`，还是清水只用于烹饪和抽象生存。
